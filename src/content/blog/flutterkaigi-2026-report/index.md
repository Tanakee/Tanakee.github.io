### FlutterWidgetPreviewerで始めるUIプレビューとVRTの自動化（あおきち）

スライド：https://speakerdeck.com/sakusaku3939/flutter-widget-previewer-de-hajimeru-ui-purebyu-to-vrt-no-jidouka

AI で UI の9割は作れるようになったものの、細かな調整は必要になります。オンボーディングや決済完了のように特定の状態でしか出ない画面は、Hot Restart のたびにその画面まで遷移し直さないといけない、という課題から始まるLTでした。

- **Flutter Widget Previewer**：`@Preview` を付けた関数を `flutter widget-preview start` で一覧表示できる。Jetpack Compose や SwiftUI のプレビューに相当する機能
- Widgetbook などの UI カタログはデザイナーとも共有しやすい一方、カタログ化する範囲が膨らんで運用が重くなりがち。Previewer は開発者が画面・Widget 単位で確認する用途向け
- Previewer は Flutter Web で動くため `dart:io` / `dart:ffi` が使えない、`main()` の初期化が走らないので DI や Provider などを組み直す必要がある、といった制約もある

そのうえで、**`@Preview` を VRT（画像比較による見た目の回帰テスト）の撮影対象としても再利用する** 仕組みが提案されていました。

1. `freezed` や `riverpod_generator` と同じく `build_runner` を使い、`@Preview` 付きの関数を検出する
2. VRT の撮影対象一覧を `vrt_previews.g.dart` に自動生成する（生成は CI で行う）
3. PR を出すと CI が画像差分を計算し、Before / After / Diff を PR コメントに投稿する

AI エージェントが実装した UI は PR 上の画像差分で確認し、細かい調整は Widget Previewer で行う、という役割分担が印象的でした。UI プレビューと VRT の二重管理をなくせるのがポイントです。

### 動画プレイヤーはなぜカクつくのか（Yoshiki Naruo）

サイバーエージェントでアプリとバックエンドを兼任されている Naruo さんのセッション。題材は、アーティストのエンタメ動画を配信するアプリ「FANBASE」です。

動画アプリは Player の実装以外にも要素が多く UI が重くなりがちで、動画を再生すると画面がもっさりする、という課題から話が始まりました。

- Flutter の描画は **UI → Raster → GPU → OS** の流れで進む
- **Raster** は描画処理を組み立てる箇所
- **シェーダー** は GPU で使う描画プログラム
- 描画エンジンの **Impeller** についても触れられていた

公式サイトの概要によると、UI スレッドと Raster スレッドの分業やフレーム落ちがどこで起きるのか、ネイティブの映像を Flutter に載せる2つの経路（Texture と PlatformView）の仕組みと向き不向き、カクつきの原因が「UI スレッド」「Raster スレッド」「ネイティブとの通信」のどれなのかを DevTools で特定する手順、といった内容が扱われていました。

<!-- 仮の感想（要確認） -->

### AIに任せられるFlutterコードベースを作る（yohei）

LayerX バクラク事業部の yohei さんのセッション。Android → Go → Flutter（約5年）と経験されてきて、今は基本的に AI にコードを書いてもらっているそうです。
題材は申請・経費精算のモバイルアプリで、SaaS の利用承認や請求書の支払い依頼などを AI が入力補助し、簡単に申請できるというものでした。

#### 課題：暗黙のルールが伝わらない

明細には按分する・しないなどの種類があり、仕様ごとに守り方を変える必要があります。
アプリエンジニア以外からの PR に対して「shield クラスを使ってね」といったやりとりが多く発生していたそうです。

#### AI向けにコードベースを作り替える「ハーネス」

**ハーネス**＝AI が道を外れず、長く走り続けられるように用意する枠。これを3つの層で作っていました。

| 層 | 性質 | 役割 |
| --- | --- | --- |
| 型 | 決定的 | そもそもの型を決めて守る |
| lint + CI | 決定的 | ルール違反を機械的に落とす |
| Skill + Subagent | 非決定的 | コードから読み取れないドメイン知識を AI に渡す |

- Good / Bad の例を渡すだけだと非決定的になるので、守らせたいものは lint で落とす
- ルールさえ決まれば AI が lint をしっかり作ってくれる。lint 作り自体もスキル化して TDD で進めている
- lint にできない知識や承認経路はスキルに渡す
- 「人が読むドキュメント」が「AI が読むスキル」になった。エンジニアが暗黙的に考えていることもスキル化する
- スキルに「いつ読むか」を書いておくと、AI が自分で読みに行く
- プラン → 実装 → テスト → レビューのフローごとに Subagent を作り、スキルを持たせる（レビューなら `review.md` など）
- モデルの精度が上がると、ガチガチに書いた md がかえって邪魔になる。モデルの成長に合わせて書き込みの粒度を変えている

#### eval：AIの振る舞いの単体テスト

- 過程は縛らずに結果で評価するので、モデルが賢くなっても対応できる
- 例：禁止された書き方を頼まれても断れるか
- AI は非決定的なので、1回ではなく3回回す

ほかにも、AI が読むものは AI が更新するループを作っていること、体験に直結する判断はまだ人が決めていて、人が見送った理由も残して次の提案で AI に読ませていることが紹介されていました。

#### 結果と今後

インターン生が大きな PR の中でも shield クラスを使っているなど、仕組み作りが生きている実感があるそうです。一方で、独自クラスの説明ができていないなど暗黙知はまだ残っていて、eval を増やすことや、ハーネス調整を全エンジニア（や AI）ができる仕組みづくりが今後の課題とのことでした。

> AIに任せられる範囲はアーキテクチャとハーネスで決まる

明日からの一歩として紹介されていたのは、

1. 今のリポジトリのアーキテクチャを AI に分析させ、ルールとぶれているところを HTML にまとめてもらう
2. 決めたルールを、型・lint・スキルのどれで守るか判断してもらう

というものでした。

<!-- 仮の感想（要確認） -->
「決定的に守るものは lint、コードから読み取れない知識はスキル」という整理がとてもわかりやすかったです。AI にコードを書いてもらうことが増えた今、ルールをどこで守るかを意識するだけでも、AI の出力の質が変わりそうだと感じました。

### その不具合、どのWidgetですか？ーアプリ内で"直せるバグ報告"を作る（Sugiy）

DeNA の iOS / Flutter エンジニアのすぎーさんのLT。

バグチケットの困りどころとして、次のようなものが挙げられていました。

- 再現手順が不明確
- 環境情報がない
- 画像や動画がない
- 画面のどこかわからない

「画面のどこ」が明確だと直しやすく、AI に修正を頼むときも「どの Widget か」がわかると伝わりやすい、という話でした。

アプリ内で画面上の要素を選んで、そのまま Issue を起票できる仕組みのデモもありました。仕組みの肝は次の4つです。

1. Element ツリーをたどり、RenderObject の位置を取る
2. `RenderBox.localToGlobal` で画面座標に変換する
3. 目印は `Semantics(identifier:)` / `ValueKey`。a11y 対応がデバッグ資産になる
4. タップ位置を含む候補のうち、面積が最小の要素を選ぶ

![仕組みの肝のスライド](./sugiy-slide.jpg)

また、ログについては「自分で溜める」のが大きなポイントとして紹介されていました。Flutter には iOS の OSLogStore 相当の API がないため、`main()` で `debugPrint` / `print` / `onError` をフックし、起動時からアプリ内のリングバッファに直近1000行を保持して、起票時に添付しているそうです。

「どの Widget か」がわかるだけでバグ報告がぐっと直しやすくなるというのは、言われてみれば当たり前なのに目から鱗でした。a11y 対応がそのままデバッグにも役立つという点も面白かったです。

### "AWSはちょっと苦手"でも大丈夫。AWS Blocksで手軽に作るFlutterのバックエンド（tacck / Kihara Takuya）

スライド：https://speakerdeck.com/tacck/aws-ha-chotto-nigate-demo-daijoubu-aws-blocks-de-tegaru-ni-tsukuru-flutter-no-bakku-endo-flutterkaigi

アプリケーションエンジニアにとって、バックエンドは言語よりも「どこに置くか（インフラ）」に苦手意識がある、という話から始まりました。AWS・Google Cloud・Azure などクラウドが多すぎてわからない、詳しくないからセキュリティが怖い…。
まずはクラウドなしで PoC として機能を確認し、確認できたらクラウドに持っていきたい、というニーズに応えるのが **AWS Blocks** です。

- バックエンドを機能単位で Block 化し、組み合わせて使う
- ローカルでも AWS でも動かせて、ローカルで動く状態からコード変更なしに AWS へデプロイできる
- 流れは「Flutter プロジェクト作成 → AWS Blocks 追加 → AI と開発」。`AGENTS.md` も整備されていて AI とスムーズに開発できる
- **sandbox**：バックエンドを AWS に出したうえでローカルから触れる

デモでは、複数ユーザー・写真のアップロード / 削除・いいね機能を持つアプリを例に、次のブロックを組み合わせていました。

| Category | Block | AWS service | 説明 |
| --- | --- | --- | --- |
| Authentication | AuthBasic | Amazon DynamoDB + JWT | 認証 |
| Data and storage | DistributedTable | Amazon DynamoDB | データベース（NoSQL） |
| Data and storage | FileBucket | Amazon S3 | オブジェクトストレージ |
| API | ApiNamespace | Amazon API Gateway | 共通エンドポイントとして動作 |
| Communication | Realtime | Amazon API Gateway WebSocket | WebSocket Pub/Sub |

まだ Preview なので本番利用はこれからで、Flutter 版は素直に使えない箇所もあるそうです。OSS なのでコントリビュートしていこう、という締めでした。

<!-- 仮の感想（要確認） -->
インフラに苦手意識があるのは自分も同じなので、ローカルで動かしたものをコードを変えずに AWS へデプロイできるのは魅力的でした。ハッカソンなどで PoC を素早く作りたいときに試してみたいです。

### AIがコードを書く時代のPRレビュー再設計ーAIが苦手な5領域を人間に渡すという選択（たまちゃん）

スライド：https://speakerdeck.com/zozotech/ai-era-pr-review-redesign

ZOZO の新規事業部のたまちゃんのLT。AI による実装が増えて人間のレビューが追いつかなくなり、AI レビューを入れても結局人間が全部見ていて二重レビューになっていた、という課題からの話でした。

そこで、AI と人間でレビューする場所を分け、人間は担当する部分だけを見るようにしたそうです。人間が見る領域として挙げられていたのが次の5つです。

1. 設計判断
2. ビジネスロジック（要件や仕様として正しいか）
3. UX
4. 暗黙知（コードやドキュメントに書かれていないもの）
5. セキュリティ方針（許容できるかどうか）

たとえば UX では、スワイプバックで入力が消えることを AI が指摘して確認ダイアログや下書き保存などの選択肢を出し、どれにするかは人間が決める、という分担です。
スライドによると、PR 作成からマージまでの中央値は 46.2 時間から 22.0 時間に短縮されたそうです。

伝えたいこととして強調されていたのは「自分たちのチームでは今どこに線を引くのか」。
銀行ならセキュリティ重視、スタートアップで人数が少ない、大手ならゆっくりしっかりやる、などチームごとに状況が違うので、線引きはチームそれぞれで考え続けるべきで、境界線をいつ引き直すのかも考え続ける必要がある、という話でした。

### 私たちはもうテストを書きませんーAIくん、あとは全て任せましたよ（Toshiki）

スライド：https://www.docswell.com/s/digitalvalue/ZQ2PNN-2026-11-02-113932

テストを書くのをやめて、「テストの作り方」を考えるようにした、というLT。対象のアプリでは、テストは全部 AI が書いているそうです。

- E2E：39画面分
- Unit / Widget テスト：285ファイル

1年ほど前から AI にテストを書かせようとしていたものの、人間がテストコードをレビューする工程を捨てきれずにいたとのこと。実際は「人間が見るべき」だったのではなく、「AI に任せるための土台を作っていなかった」だけだった、という気づきが印象的でした。

#### 土台づくり

- 暗黙知をスキルにして渡す。ただしスキルにして渡せばいいだけではなく、テストを6段階に分けている
- 最初に「やらない」ことを決める。Unit テストは `lib` 配下のファイルすべてを対象にしている
- AI は「多分こう動く」という推測でテストを書きがちで、それだと機能ではなく予測に対するテストになってしまう。なので先にコードなどの根拠を読ませてから書かせる
- 品質規約は11本。すべて、レビューで誰かが言っていたことを言語化・スキル化したもの
- 落ちたテストを、通るように曲げさせない

#### PASS を疑う

実際にデグレが起きたときにちゃんと fail するのか、対象機能をわざと壊したら赤くなるのかを検証したところ、

- E2E：39画面中17画面のテストが意味のないテストだった
- Unit：3050件中70件が意味のないテストだった

ということがわかったそうです。原因は「スキルの一文が AI の癖になる」こと。たとえば「最低3観点」と書くと無理やり3観点を出し、「既存を踏襲」と書くと探索をやめてしまう。
スキルを改善した結果、37/37件で期待通りのテストができ、Unit テストも改善されたとのことでした。

> 書く前に決めさせる / 通るように曲げない / PASSを疑う

### FlutterのUI/UX向上ガイド：50か国以上での開発事例から見えた知見（Kenichi Kambara）

スライド：https://speakerdeck.com/korodroid/flutterkaigi-building-better-flutter-ux-insights-from-50-plus-countries

リアルタイム翻訳アプリ「SekaiPhone Pro」や語学学習アプリ「SekaiPals」を作っている Kambara さんのセッション。
実際に50か国以上に行ってアプリを使ってみたところ、翻訳はできても UX が良くない、という気づきがあったそうです。翻訳だけでなく、文化・方向・画面サイズ・利用環境まで含めて UX を設計する必要がある、という内容でした。

スライドで紹介されていた主なトピックは次のとおりです。

- **音声 UI**：結果が返るまで待たせるのではなく、話している最中から認識状況を見せる。Listening / Processing / Completed / Error の4状態を設計する
- **オンボーディング**：最初に全部説明しても忘れられるので、「どれだけ説明するか」より「いつ案内を出すか」を設計する
- **RTL 対応**：`left` / `right` ではなく `EdgeInsetsDirectional` や `AlignmentDirectional` で「読む方向」を表現する。戻る矢印は反転し、飛行機アイコンやロゴは反転しない
- **レスポンシブ / アダプティブ**：広い画面では単純に拡大せず、`LayoutBuilder` でリスト＋詳細の2ペインに組み替える。翻訳で文字列の長さが大きく変わることにも備える
- **文化の違い**：色やジェスチャーの意味は地域によって変わる。決めつけず、テストとフィードバックで確かめる
- **AI との分担**：翻訳案や RTL 観点の洗い出しは AI、現地の文脈の理解や違和感の判断は人間

明日からできることとして、端末の言語を RTL に切り替えて主要画面を確認する、文字列の長さを3倍くらいにして崩れを探す、が挙げられていました。

50か国以上で実際に使ってみたからこその知見で、「翻訳するだけでは足りない」という話に説得力がありました。端末の言語を RTL に切り替えて画面を確認する、というのはすぐにでも試せそうです。
